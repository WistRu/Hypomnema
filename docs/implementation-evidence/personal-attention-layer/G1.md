## Importance, provenance and replay proof

Feature-on behavior:

- duplicate browser rows resolve to one logical page;
- a user web write records `user/manual` and projects the value to all copies atomically;
- the agent route records `agent/on_behalf_of_user`; client-supplied provenance is not accepted;
- missing IDs abort the entire operation;
- value `0` is canonical `unrated` and stores null provenance;
- identical user, agent and clear replays preserve preference `importance_updated_at`, preference `updated_at` and audit `reviewed_at` while repairing any drifted compatibility projection.

The final built MCP stdio runtime transcript on schema 18 returned 16 tools and exposed `set_importance` as a deprecated, non-destructive, idempotent compatibility alias with a strict input schema.

- Feature off: MCP returned `{updated:1, importance:1}` for tab 1. Its logical group remained `[1:1, 3335:2, 6669:0]`; canonical preference stayed null and the conflict audit stayed unreviewed.
- Feature on: two identical MCP calls for tab 2 returned the same `{updated:1, importance:2}` result. Its three browser copies became `2`; canonical provenance was `agent/on_behalf_of_user` and the audit became confirmed.
- Rollback on the same schema-18 DB: after switching back off, MCP set tab 2 to `3` while sibling copies remained `2`; the canonical preference remained value `2`, `agent/on_behalf_of_user`, with the same timestamps.

The adapter negotiates `GET /api/features` for every deprecated mutation: `true` uses `/api/agent/tabs/importance`, `false` uses `/api/tabs/importance`, exact schema-17 `404` uses the legacy route, and malformed/503/network responses fail before any PATCH.
