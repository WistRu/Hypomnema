## Why the corrective seam was required

The accepted C82c ledger could replay an exact agent command before mutable
corpus validation only after a syntactically complete run approval reached the
server. A stateless MCP process cannot reconstruct an old estimate and approval
fingerprint after restart. If it called preflight first, corpus/privacy drift
could instead return a new confirmation requirement and make the durable receipt
unreachable. Process memory or fabricated derived values would violate the
accepted replay and safety boundaries.

C82d therefore adds one deep composition endpoint:

```text
POST /api/agent/research/start
```

Its strict declarative body contains only version, target, question,
shareable-context choice, source cap, budget, exact confirmed-origin digest
sets, idempotency key and authorization reference. It rejects parent report,
capture intent, estimate, approval fingerprint and provenance. The server fixes
`parentReportId=null`, an empty capture intent and
`agent/on_behalf_of_user` provenance.

## Replay and new-start ordering

The endpoint executes the following closed order:

1. feature check and strict request parse;
2. durable receipt lookup using the canonical declarative fingerprint and
   authorization hash;
3. exact receipt replay as the original `JobRef`, before provider, target,
   corpus or current confirmation validation;
4. provider availability for a genuinely new command;
5. a second receipt check immediately before synchronous mutable preflight;
6. write-free typed `confirmation_required` or server-derived atomic submit.

The shared strict response is either a research `DurableJobRef` (`202`) or only
`{status:"confirmation_required", confirmationRequirements}` (`200`). No URL,
origin display, source/corpus/report material or raw authorization value enters
the response or receipt. The canonical bytes exactly equal the pre-existing
C82c receipt fingerprint for a null-parent, empty-capture approval.

## Real application proof

Disposable real schema-24 applications prove:

- an unconfirmed authenticated start returns typed confirmation with zero
  jobs, runs or receipts;
- exact confirmation creates one agent-owned research job/run/receipt;
- access/corpus drift changes current confirmation requirements and makes a new
  preflight unapprovable, yet the exact original declarative command returns the
  same job without a second write;
- the same receipt still replays after its Resource target becomes merged and
  unavailable;
- closing the provider-backed app and reopening the same database without a
  provider still returns the original job, while a new key returns exact `503`;
- changed question, confirmed digests or authorization under the same key return
  `IDEMPOTENCY_KEY_CONFLICT`;
- the existing C82c full-approval path and the new declarative path share the
  same receipt bytes and job identity.
