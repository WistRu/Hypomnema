## REST, local capability and privacy-negative evidence

The local UI routes require a server-side HttpOnly same-origin session. Pairing
uses a short-lived one-time challenge and a hashed per-installation credential;
the stored plaintext credential is never persisted. Tests cover two
installations on one origin, rotation, generic failure for origin/install/code
mismatch, bounded attempts/expiry, transactional challenge invalidation on
revoke and fail-closed malformed capability state.

Live pairing exposed one integration defect before gate acceptance: Chromium
omitted the `Origin` header on credentialed extension `GET` requests, so the
server returned `401` even though the credential and stored extension origin
were valid. The repaired contract uses the shared canonical
`x-tabhub-extension-origin` header. The extension supplies its runtime origin;
the server binds that value to the stored capability origin and rejects any
explicit/actual origin mismatch. Targeted authentication and CORS tests pass,
including the negative mismatch path. No capability is moved to a URL or log.

Protected Library context mode uses separate local companion routes:

- `/api/local/tabs`
- `/api/local/tabs/bulk-ids`
- `/api/local/tab-instances/library-bulk`

The ordinary public routes remain private-blind. Local Library search returns
only current active unsuperseded context heads: user/system entries or currently
accepted agent entries. Withdrawn, superseded, rejected, unreviewed and
`local_only` data do not appear in agent/public projections.

Privacy-negative control/hidden tests prove byte-identical agent read, search
and receipt output despite additional local-only page context and exact-tab
intent. No hidden count, hidden existence signal, private body, internal ID,
revision or idempotency key is exposed. Candidate structured logs contain only
method, route template and status; inspected output contains no request bodies,
query values, credentials or private page text.

## Extension exact-target and offline evidence

Automated extension tests verify that Save, Archive and Promote carry the exact
scope and expected page rendered in the popup. Background processing re-reads
the active tab and current snapshot, rejects page-A operations after navigation
to page B, serializes the mutation transport, and keeps feature-off at zero POST,
zero enqueue and unchanged durable queue state.

Offline Save uses a stable idempotency key. Stale-head discard is explicit and
user-confirmed, background-owned and serialized; a retry-alarm/discard race
sends the successor exactly once. Crash after server success but before local
ACK replays the same idempotency key. Pairing revocation returns the popup to a
generic pairing state. Queue metadata now accepts only strict UUID and ISO-date
values. A dedicated offline Archive/Promote regression queues on page A,
navigates the same physical tab before retry, and proves the stale mutation is
rejected rather than applied to page B.

The remediated lifecycle contract persists immutable `scope` and `expectedPage`
for Archive and Promote. Every retry first posts a refreshed snapshot, then
performs the native exact-tab check, and sends no lifecycle command when the
physical target is stale. The server independently compares installation,
browser session, browser tab, logical page, URL, normalized URL and instance
revision against both the intent owner and current physical row. Real-server
tests cover navigated stale targets and forged scope/page payloads.

`promoted_context_entry_id IS NULL`, matching `context_entries=0`,

failure followed by navigation cannot promote page A as page B.
